# DSH-Go portable build

English | [中文](README.zh.md)

DSH-Go is a Windows portable build of [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) (MIT): every runtime file is kept in the `portable\` directory beside the executable, the whole directory can be moved to any path (including a network drive), and double-clicking the executable restores the state from the previous shutdown.

This project is not an official DeepSeek release and carries no official endorsement. The maintainer cannot write code; every change beyond the upstream project was generated by the AI model DeepSeek V4.1 Flash and has not been reviewed by any qualified engineer. Read the diff first, back up `portable\`, and accept the risk yourself.

## Directory layout

```
DSH-Go\
├─ DeepSeek Harness.exe     启动入口，内置便携引导
├─ resources\ ...           Electron、asar、自带 Node/pnpm 运行时
└─ portable\                唯一的数据根
   ├─ dsh-home\             $DSH_HOME：sessions\ storages\ profiles\ attachments\ .credentials.yaml
   ├─ user-data\            Electron profile：Local Storage、desktop\settings.json、logs\
   ├─ workspace\            默认工作区父目录（实际工作区为 workspace\deepseek-harness\default-workspace）
   ├─ cache\                npm / pnpm 缓存、Chromium 缓存，兼作 XDG_CACHE_HOME
   ├─ config\               XDG_CONFIG_HOME：遵守 XDG 规范的工具与插件的配置
   ├─ state\                XDG_STATE_HOME：同上，日志与运行状态
   ├─ logs\                 宿主控制台日志 host-<日期>.log，保留最近 7 天
   ├─ temp\                 Electron 临时目录
   └─ state.json            上次启动所在的目录，用于识别"搬家"
```

Program files and data are fully separated: an upgrade replaces only the program files, and `portable\` stays as it is.

`logs\` is the first place to look when diagnosing a problem: the portable build has no terminal you can roll back from, so warnings such as a refused delete, a failed cache cleanup, or a failed relocation rewrite are written only here, one file per day, with records older than 7 days cleared at startup.

Plugins do not need to be rewritten for the portable build: at startup it points `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, and `XDG_STATE_HOME` at `config\`, `cache\`, and `state\`, so plugins and tools that locate their files per the XDG spec (billion-context is one example) keep configuration, cache, and logs inside `portable\`, and they move along with the directory.

## What happens during a move

At startup it compares `lastRoot` in `state.json` with the current executable directory.

| Difference | Action |
|---|---|
| Directory unchanged | Do nothing |
| Directory changed | Rewrite every saved absolute path: `storages\workspace.json`, the session logs (decompress each zstd frame → replace → recompress, recompute the checksum), and the YAML/JSON under `profiles`, and change each session's project directory to the name derived from the new path |
| Derived cache | Delete `storages\session_projcache`; it is rebuilt on the first retrieval |

The rewrite count and failure reasons are printed to the console log; a single failed file does not block startup.

## Network drives

Measured conclusion: a network share can hold the data in `portable\`, but **whether you can double-click and run depends on whether the share grants execute permission**. If the share maps the login account to an identity with only read and write, Windows refuses to start the executable with `Access is denied` (copying it over with the system's built-in `where.exe` fails to run as well, and `icacls` shows that identity has `(R,W)` but no `(X)`). In that case keeping the whole directory on the share is only good for backup and transport; running still needs a local disk.

The data plane itself works over SMB: this project's session logs (checksummed zstd frame appends) and session search database (SQLite WAL) both passed measurement on a share.

Running on a share also behaves differently in one way: Windows' write-restriction sandbox needs to write access control entries (ACLs) at the workspace root, and ACLs cannot be written on a share directory, so when the executable is on a UNC path or a mapped network drive, DSH-Go starts with `danger-full-access`. To force the sandbox back, set `DSH_PERMISSION_MODE=workspace-write`; on a local disk the default stays `workspace-write`.

Two more things to watch on a share: only one machine may open the same `portable\` at a time (concurrent writes corrupt session logs); the first launch reads over 7,000 files, so a cold start is noticeably slower than on a local disk.

## Deleting a session (built into DSH-Go)

DSH-Go adds a **Delete session** row to the session row's `⋯` menu, below **Archive session**. It performs a permanent delete: after confirmation it removes that session's session-log directory and drops it from the workspace row, the archived set, and the pinned set, unlike archiving (which only changes grouping and keeps the log). Selecting it always opens a confirmation first that states the session title and "cannot be recovered"; if the session is still running, the host stops its tasks before deleting and does not refuse; if it truly cannot delete, it explains why (the session no longer exists, or the backend reports a hold it cannot clear).

This row is provided by the installer's built-in bundle `@deepseek-ai/dsh-go-session-delete`, enabled by default in the `web` profile template. It is listed in the plugin manager as an optional "provided with the installer" bundle and can be turned off and on again directly in the main list; once off, the menu row disappears and saved sessions are unaffected. Bundles distributed with the program do not support "uninstall" (this is DSH's rule for every built-in bundle — a real uninstall means changing the program files); to disable one, turn it off. It has no keyboard shortcut.

Host capabilities (`workspace.deleteSession` and `SessionPersistence.delete`) are core, so this bundle provides only the interface, and the host decides whether the delete succeeds. Before deleting, the host sends `workspace/session-close` to release the in-process holders still alive for that session (the Agent registry closes its log write handle), so a session you just chatted in and still have open can be deleted directly without a restart; when the release fails, the persistence backend reports the hold it cannot clear. After deletion the backend emits `session/deleted`, and the projection cache discards that session's checkpoint records accordingly, so reusing the same id later does not read stale data.

## Maintenance (cleaning up leftovers)

The settings page has a **Maintenance** section, provided by the built-in bundle `@deepseek-ai/dsh-go-maintenance`. Clicking **Scan** lists three kinds of leftovers: projection-cache checkpoints that no workspace references, log directories that no workspace references, and image attachments that no log references; you can clean up one kind at a time or all at once, and it rescans automatically after cleaning.

"Alive" is decided by workspaces: every workspace's sessions, plus the archived and pinned sets. A session whose log still sits on disk but that no workspace owns is residue — exactly the directories earlier builds left behind when a Session was deleted, invisible in the UI and impossible to remove there. When no workspace references anything at all, the scan reports nothing rather than calling the whole installation residue. Before a Session directory is removed, the Host also confirms no work is still running on it.

It works only on click and never scans at startup — the longer the installation lives, the slower a startup scan would be. Anything it cannot judge is left untouched: when one session log cannot be read, no attachment is cleaned up this run; when the persistence backend keeps no directory, no orphan directory is reported either. Every clean writes one audit line into the Host log under `logs\`. The cost ledger keeps the billing history of deleted sessions and is not part of this.
## Credentials

`portable\dsh-home\.credentials.yaml` is plaintext and moves with the directory, so a new machine needs no new login. Delete it before sharing, uploading, or committing.

## Official auto-update disabled

The portable build cannot be overwritten by the installer (that would move the directory into Program Files), so the official mandatory update check is disabled; the unpacked auto-update configuration was never part of the unsigned directory build anyway.

An upgrade replaces the program files and keeps `portable\`. For source-level updates (following the official repository), see [SYNC.md](SYNC.md); for the build method, see [BUILD.md](BUILD.md).

## Updating itself

The program directory contains `Update-DSH-Go.ps1`; double-click it or run it in PowerShell:

```powershell
pwsh .\Update-DSH-Go.ps1          # 下载最新发布版并替换程序文件
pwsh .\Update-DSH-Go.ps1 -Check   # 只检查有没有新版本
pwsh .\Update-DSH-Go.ps1 -Force   # 关闭正在运行的实例后更新
```

It reads the latest version from GitHub Releases (comparing against the commit hash in `BUILD-INFO.txt`), downloads the zip, **verifies SHA-256**, and then overwrites the program files; `portable\` is not touched. Updating needs network access, and once the repository is public no token is needed.

If a new version starts abnormally, swap the old version directory back in wholesale; the data is always in `portable\` and unaffected.
